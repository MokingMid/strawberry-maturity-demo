## 2. 架构决策（已定）

```
图片/视频帧
  → letterbox 640
  → YOLO11n（1 类：strawberry）
  → NMS / 置信度 / 面积过滤
  → 每个框外扩 10%–15% → 补方形 → ROI
  → ResNet18（3 类：ripe / half / unripe）
  → 后处理 → 跟踪 → 虚拟线越线计数
  → 标注帧 + CSV + 计数
```

三条路线：

| 路线 | 结构 | 作用 |
|---|---|---|
| A 主线 | 1 类检测 + 3 类分类 | 检测器只学“草莓在哪”，不受 half 稀缺拖累；分类器用 GT 框 ROI 训练 |
| B 消融 | 3 类检测（YOLO 直接输出状态） | 回答“把状态放进检测头是否更好”；half 很可能学不好，作为对照 |
| C 传统基线 | HSV 颜色矩/直方图 + GLCM + LBP + SVM | 回答“深度学习比传统特征提升多少” |

**为什么检测器用 1 类**：half 只有 11 个框 / 3 个独立场景，3 类检测头大概率学不会 half；1 类检测只学定位，稳得多。三分类放在第二段。

**为什么分类器用 GT 框 ROI**：现成的 `traditional_cv/output/单果区域` 是算法轮廓，含叶片、手部、粘连，不能训练；必须用标注框重新裁。

**为什么按场景组划分**：数据里有 7 对翻转/缩放重复图（57 个独立场景），随机划分会让验证/测试指标虚高。

**为什么工作目录用 `work`**：项目路径含中文，Ultralytics/OpenCV 在 Windows 中文路径下有时读不到图；训练产物统一写到 ASCII 目录，源数据不动。

## 9. 关键规则与理由

| 规则 | 理由 |
|---|---|
| 检测器 1 类 | half 只有 11 框 / 3 场景，3 类检测头学不会；定位与分类解耦 |
| 分类只用 GT 框 ROI | 算法裁剪含叶片/手/粘连；GT 框才是干净单果 |
| 外扩 12%、补方形 | 保留少量上下文；分类输入一致；贴边/邻果自适应缩小 padding |
| 贴边框默认跳过 | 截断果实分类标签不可靠；检测仍保留这些框 |
| 按 scene_group 划分 | 7 对翻转/缩放重复图，随机划分会泄漏 |
| 轻度 HSV 增强 | 颜色是成熟度线索，不能大幅改色相 |
| 类别权重 balanced | half 极少，必须加权；但权重不能替代补数据 |
| 小数据检测用低 LR | 45 图 / batch8 下 lr0=0.001 + cos_lr 稳定；lr0=0.002 在 epoch2 后崩塌 |
| 检测 conf 在 val 调 | 0.55 使 val P/R 1.0、count_err 0；test 只报告，不再调 |
| 分类器看 per-class/support | val 只有 30 张、half 3 张；macro F1 1.0 不能当泛化 |
| 测试集冻结 | 一旦确定 split，不再重划；报告用同一份清单 |
| 工作目录 ASCII | 避开 Ultralytics/OpenCV 中文路径问题 |
| YOLO split txt 写绝对路径 | Ultralytics 8.4 不会把 txt 里的相对路径拼到 `data.yaml` 的 `path` 上；相对路径会从 cwd 找图，报 `corrupt image`。改工作目录后要重新导出 |
